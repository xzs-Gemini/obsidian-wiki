# 如何向 Codex 下任务

你最适合的提示词不是一段极长的“万能咒语”，而是一个清晰的任务合同。

## 六要素

1. **目标**：最终要得到什么。
2. **对象**：在哪个文件夹、项目、应用、场景或文档中工作。
3. **现状**：已知进度、当前问题和可用材料。
4. **边界**：哪些能改，哪些不能改，是否允许联网、安装、生成素材、发送或发布。
5. **验收**：用什么证据算完成。
6. **交付**：输出放哪里，最后怎样汇报。

## 推荐句式

```text
请在【对象】中完成【目标】。

先检查【现状/材料】，确认真实基线后再修改。
允许修改：【范围】。
不要修改：【禁止项】。

完成后必须验证：【测试、运行流程、截图、数量或结构检查】。
如果某一步无法真实验证，明确写成“未验证”，不要把推测当成完成。
最终给我：【文件/报告/简短结果】，保存在【路径】。
```

## 适合你的补充约束

- “保持其他行为不变。”
- “先做只读审计，确认根因后再实施。”
- “不要覆盖原文件，另存新文件。”
- “每完成一批就运行检查并记录断点。”
- “不要为了通过测试伪造数据、跳过流程或修改验收条件。”
- “先用结构化工具或 MCP；只有必须看 GUI 时再用 Computer Use。”
- “只修最小原因，不顺手重构无关区域。”

## 什么不要写

```text
帮我优化一下。
```

这句话缺少对象、范围和完成定义。改成：

```text
请审计这个页面的移动端布局。先截图并列出可复现问题，只修改间距、字号与溢出问题，不改业务逻辑和配色。完成后在 390×844 与 1920×1080 两个视口验证，并给出修改文件和残留风险。
```

## 何时允许 Codex 自主推进

当选择不会改变任务方向、不会产生重大外部副作用时，可以直接说“按最佳判断继续”。如果不同选择会显著改变产品、数据、成本、账号权限或公开结果，应要求先停在决策点。
