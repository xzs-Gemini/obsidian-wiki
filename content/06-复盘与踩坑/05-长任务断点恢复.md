# 长任务断点恢复

## 为什么长任务容易失败

- 对话上下文被大量日志污染；
- 显示顺序变化导致跳项或重复；
- 中断前数据尚未落盘；
- 累计数与真实数据库不一致；
- 新窗口从头推断，覆盖已完成内容；
- 把“任务仍能继续”误写成完成或阻塞。

## 固定队列

使用唯一 ID + `queueIndex`，明确状态：

```text
pending → researching/working → completed
                         ↘ blocked/review_required
```

状态写入与实际数据落盘要有确定顺序，避免队列显示完成但结果缺失。

## 检查点内容

- 任务总量与累计完成量；
- 当前批次范围；
- 最后完成 ID；
- 下一 ID；
- 数据/证据/文件累计数量；
- 运行过的检查和结果；
- 不能碰的范围；
- 是否有未提交/未落盘内容；
- 当前服务与应用状态。

## 恢复流程

1. 完整读取 Handoff；
2. 只读复核关键基线；
3. 检查最后完成项和下一项是否吻合；
4. 核对无重复/缺失；
5. 若不一致先修复断点，不继续新批次；
6. 从明确 ID 恢复；
7. 在下一个检查点重新生成报告。

## 状态使用

- `Paused`：安全停在断点，未来可继续。
- `Blocked`：关键外部条件缺失，当前无法有意义推进。
- `Complete`：所有必做验收已经完成。

任务很长、很难或尚未做完，不自动等于 Blocked；预算接近结束也不等于 Complete。
