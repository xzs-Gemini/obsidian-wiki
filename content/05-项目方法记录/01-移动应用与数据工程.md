# 移动应用与数据工程

## 项目抽象

一个包含大量地点记录、图片、无障碍信息与普通出行建议的移动应用。工作既包括 React Native/Expo 前端，也包括 SQLite、本地图片库、研究证据库、数据迁移、筛选与预览服务。

## 你的工作思路

### 1. 先把数据问题从 UI 问题中拆出来

最初容易把“页面显示不对”当成前端问题。你的做法逐渐变成先盘点所有数据源、字段、ID、状态和适配器，再决定 UI。先建立独立数据库，再通过统一模型连接应用。

### 2. 以稳定 ID 作为主轴

所有图片、无障碍证据、旅游建议和界面记录都通过唯一 `scenicId` 关联，而不是名称或数组位置。这样可检测缺失、重复、错位与孤立记录。

### 3. 单一事实源 + 派生数据

把主数据库作为权威来源；兼容清单、静态图片映射、报告和缓存都由生成脚本派生。生成应幂等，任何时候都能从源数据重建。

### 4. 事实研究采用保守三态

有证据、冲突、无可用真实数据应明确区分。没有可靠来源时保留未知，不为提高覆盖率编造设施或把搜索摘要当事实。

### 5. 大批量任务使用固定队列

用唯一 ID 队列推进，按小批次保存和验证。中断时记录下一 ID、累计数量、检查结果和未落盘内容，避免跨窗口重做或跳项。

## 主要坑

### 图片“存在”不等于图片正确

- 占位图可能被错误标为可用；
- 文件名和 manifest 对得上，但语义是另一个同名地点；
- EXIF 缺失导致物理方向错误；
- 尺寸达标但主体裁切失败；
- 来源存在但版权/授权状态不清。

解决：结构检查 + 元数据检查 + 联系表人工审阅 + 权利状态分层。

### 数据库更新不等于 App 已读取新数据

SQLite 可能因为版本门槛、缓存或初始化逻辑继续使用旧数据。必须验证应用适配器、实际运行时记录和升级/重建路径。

### 预览 URL 可用不等于整条链路可用

本地 Metro、隧道、manifest 和 bundle 是不同环节。旧隧道可能仍活着而 Metro 已退出。必须逐层检查 HTTP 状态和实际 Bundle。

### Windows npm 缓存与锁文件

错误的缓存路径、EPERM 和被占用的依赖目录可能让安装留下半完成状态。修复后要重新从依赖完整性开始跑全套预检，不能直接从失败处往后跳。

### Git 元数据缺失

有 `.git` 目录不代表存在有效仓库。没有 HEAD/objects/config 时不能声称已提交、合并或有可恢复历史。

## 可复用验收

- 唯一 ID 数量、重复、缺失、孤立引用；
- 类型检查与数据 schema；
- 数据库生成幂等性；
- App 两条读取路径一致；
- 筛选/搜索结果符合事实语义；
- 图片结构 + 视觉联系表；
- Expo Doctor、导出、manifest、bundle；
- 浏览器/设备用户流程；
- 不把设备未连接时的自动化检查写成真机验收。
