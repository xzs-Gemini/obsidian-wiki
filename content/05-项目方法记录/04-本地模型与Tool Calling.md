# 本地模型与 Tool Calling

## 项目抽象

把本地大模型服务连接到 Unity 内的 AI 行为系统，使用 OpenAI 兼容接口进行聊天与工具调用，再由业务层执行工具并反馈结果。

## 你的工作思路

### 1. 分层验收

```text
进程存在
→ 端口监听
→ /v1/models
→ 普通 Chat Completion
→ 单工具调用
→ 工具结果回传
→ 多工具完整协议
→ Unity 业务候选
→ 真实游戏循环
```

任何一层失败，都不能用下一层的假回退冒充成功。

### 2. 先验证 Provider，再接业务

在修改 Unity/CoreAI 前，先确认本地服务、模型名、Endpoint 拼接、Tool schema、返回格式和工具结果 roundtrip。这样能避免把模型能力问题误判成游戏代码问题。

### 3. 用重复试验识别不稳定性

一次成功的 Tool Calling 不能证明稳定。完整业务需要模型按协议调用一组必要工具；连续多次遗漏某个工具，说明模型或提示词的协议遵循不稳定。

### 4. 安全回退要“诚实失败”

业务可有安全 fallback，但报告中必须区分“AI 候选通过”和“候选被拒后回退”。Fallback 不是本地模型验收通过。

## 主要坑

- 服务配置里写了 `127.0.0.1` 不代表端口真的监听。
- `/v1/models` 连接拒绝时，不应继续跑工具协议。
- 模型下载受网络、镜像和超时影响；换来源后要校验哈希与文件完整性。
- 小模型能完成简单单工具调用，但在多工具强约束业务中可能漏调用。
- 模型名、基础 URL 与最终 `/chat/completions` 拼接容易重复 `/v1` 或使用不存在的 ID。
- 业务框架自动执行工具后，仍需确认工具结果被正确回传到模型。

## 可复用验收

- Endpoint 和模型 ID 真实存在；
- Tool schema 与解析类型一致；
- 至少一次真实工具结果 roundtrip；
- 多次完整工具集测试；
- 业务拒绝原因可观测；
- fallback 与 success 独立统计；
- 不在报告中记录 API Key、Token 或敏感 Prompt。
